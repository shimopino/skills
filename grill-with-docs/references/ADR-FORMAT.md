# ADR Format

ADR は `docs/adr/` に配置し、連番で命名する：`0001-slug.md`、`0002-slug.md` など。

`docs/adr/` ディレクトリは最初の ADR が必要になったときに遅延作成する。

## テンプレート

```md
# {決定の短いタイトル}

{1〜3 文：何の文脈で、何を決定し、なぜそうしたか。}
```

以上。ADR は 1 段落でよい。「決定が行われた」という事実と「なぜ」を記録することに価値がある。セクションを埋めることではない。

## 任意セクション

本当に価値がある場合のみ含める。ほとんどの ADR には不要：

- **Status** フロントマター（`proposed | accepted | deprecated | superseded by ADR-NNNN`）— 決定が見直された場合に有用
- **検討した選択肢** — 却下した代替案を後で参照する価値がある場合のみ
- **影響** — 非自明な下流への影響を明示する必要がある場合のみ

## 番号付け

`docs/adr/` 内の最大番号をスキャンして 1 を加える。

## ADR を提案するタイミング

以下の **3 条件をすべて満たす**ときのみ：

1. **取り消しが難しい** — 後から考えを変えるコストが相当かかる
2. **コンテキストなしでは奇妙に見える** — 将来の読者がコードを見て「なぜこうしたのか？」と疑問に思う
3. **本物のトレードオフがあった** — 複数の選択肢があって特定の理由でこれを選んだ

決定が取り消し可能なら記録不要——単に取り消せばよい。奇妙に見えないなら誰も疑問に思わない。本物の代替案がなかったなら「明らかなことをした」以上のことを記録するものがない。

**ADR よりコード・コードコメントを優先する。** コードやコメントで決定を明確に表現できる場合はそちらを選ぶ。コード自体から判断できない場合のみ ADR に昇格させる。

### ADR に適した内容

- **アーキテクチャの形状。** 「モノレポを採用する」「書き込みモデルはイベントソーシング、読み取りモデルは Postgres に投影する」
- **コンテキスト間の連携パターン。** 「Ordering と Billing は同期 HTTP ではなくドメインイベントで通信する」
- **ロックインを伴う技術選定。** データベース、メッセージバス、認証プロバイダー、デプロイ先。全ライブラリではなく、入れ替えに四半期かかるものだけ。
- **境界とスコープの決定。** 「顧客データは Customer コンテキストが所有し、他コンテキストは ID のみで参照する」明示的な「やらないこと」は「やること」と同じくらい価値がある。
- **明白な道からの意図的な逸脱。** 「ORM ではなく手書き SQL を使う理由は X だから」合理的な読者が逆を想定する箇所はすべて記録する——これにより次のエンジニアが意図的な設計を「修正」してしまうことを防ぐ。
- **コードに見えない制約。** 「コンプライアンス要件により AWS は使えない」「パートナー API 契約でレスポンスタイムは 200ms 以内でなければならない」
- **却下が非自明な代替案。** GraphQL を検討して微妙な理由で REST を選んだなら記録する——さもなければ半年後に誰かが GraphQL を再提案する。
