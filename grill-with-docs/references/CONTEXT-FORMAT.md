# CONTEXT.md Format

## Structure

```md
# {コンテキスト名}

{このコンテキストが何であり、なぜ存在するかを 1〜2 文で説明する。}

## 用語

**注文（Order）**:
利用者が商品を購入する意思を表明した記録。
_使わない_: 購入、トランザクション

**請求書（Invoice）**:
配送完了後に顧客へ送付する支払い請求。
_使わない_: 請求書類、支払い依頼

**顧客（Customer）**:
注文を行う個人または組織。
_使わない_: クライアント、買い手、アカウント
```

## Rules

- **意見を持つ。** 同じ概念に複数の言葉がある場合、最良の一つを選び、避けるべき別名を列挙する。
- **曖昧さを明示する。** 用語が複数の意味で使われている場合は「曖昧な用語」として明記し、解決策を示す。
- **定義は簡潔に。** 最大 1〜2 文。「何であるか」を定義し、「何をするか」は書かない。
- **このプロジェクト固有の用語のみ含める。** タイムアウトやエラー型など一般的なプログラミング概念は、プロジェクトで頻繁に使われていても記載しない。追加前に「このコンテキスト固有の概念か、一般的なプログラミング概念か？」と問う。前者だけを記載する。
- **自然なまとまりがあれば小見出しでグループ化する。** 全用語が単一の領域に属するなら、フラットなリストでよい。

## 含めないもの

- ドメインルール、不変条件、制約（「注文には必ず顧客が存在する」など）
- コンテキスト間の関係図（CONTEXT-MAP.md に書く）
- 実装詳細、仕様、メモ
- ADR の内容

## 単一コンテキストと複数コンテキスト

**単一コンテキスト（多くのリポジトリ）:** リポジトリルートに `CONTEXT.md` を 1 つ配置する。

**複数コンテキスト:** ルートに `CONTEXT-MAP.md` を置き、各コンテキストの場所と相互関係を記述する：

```md
# コンテキストマップ

## コンテキスト一覧

- [注文（Ordering）](./src/ordering/CONTEXT.md) — 顧客注文を受け付けて追跡する
- [請求（Billing）](./src/billing/CONTEXT.md) — 請求書を生成して支払いを処理する
- [配送（Fulfillment）](./src/fulfillment/CONTEXT.md) — 倉庫でのピッキングと出荷を管理する

## コンテキスト間の関係

- **Ordering → Fulfillment**: Ordering が `OrderPlaced` イベントを発行し、Fulfillment がそれを消費してピッキングを開始する
- **Fulfillment → Billing**: Fulfillment が `ShipmentDispatched` イベントを発行し、Billing がそれを消費して請求書を生成する
- **Ordering ↔ Billing**: `CustomerId` と `Money` の型を共有する
```

スキルは以下のルールで構造を判断する：

- `CONTEXT-MAP.md` が存在する → 読み込んでコンテキストを把握する
- ルートに `CONTEXT.md` のみ存在する → 単一コンテキスト
- どちらも存在しない → 最初の用語が確定したときにルートの `CONTEXT.md` を遅延作成する

複数コンテキストがある場合、現在のトピックがどのコンテキストに関連するかを推定する。不明な場合は確認する。
