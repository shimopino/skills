<what-to-do>

このプランのあらゆる側面について、共通理解に達するまで私に徹底的に質問してください。設計ツリーの各分岐を順番に辿り、依存関係のある決定を一つずつ解消してください。各質問では推奨回答も提示してください。

質問は一度に一つずつ聞いてください。次の質問に進む前に、各質問への返答を待ってください。

コードベースを探索することで答えられる質問は、直接探索して確認してください。

</what-to-do>

## モード

ユーザーの意図からモードを判断してください：

- **設計モード**（デフォルト）：計画を叩き台として検証し、用語を整理し、CONTEXT.md・DOMAIN-RULES.md・ADR に決定事項を記録する。
- **学習モード**：馴染みのないコードを一緒に読み解く。ユーザーに特定のシンボルを探させ、見えているものを説明させ、動作を予測してもらってから正解を示す。理解が進むにつれてキーコンセプトをまとめる。ドメイン用語が出てきた際は CONTEXT.md を更新する——理解とドキュメントは互いを強化し合う。

## ドメイン認識

コードベースの探索と合わせて、既存ドキュメントも確認してください。

### ファイル構造

多くのリポジトリは単一コンテキスト構成：

```
/
├── CONTEXT.md
├── DOMAIN-RULES.md     ← 一時的。ルールがすべてコード化されたら削除
├── docs/
│   └── adr/
└── src/
```

ルートに `CONTEXT-MAP.md` があれば複数コンテキスト構成：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                ← システム全体の意思決定
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   ├── DOMAIN-RULES.md ← 一時的。ルールがすべてコード化されたら削除
    │   └── docs/adr/       ← コンテキスト固有の意思決定
    └── billing/
        ├── CONTEXT.md
        ├── DOMAIN-RULES.md
        └── docs/adr/
```

以下のルールで構造を判断します：

- `CONTEXT-MAP.md` が存在する → 読み込んで各コンテキストとその場所を把握する
- ルートに `CONTEXT.md` のみ存在する → 単一コンテキスト
- どちらも存在しない → 最初の用語が確定したときに遅延作成する

ファイルは必要になってから作成します。空のドキュメントは作らないでください。

ファイル読み込みとコード照合は**現在開いているリポジトリのみ**を対象にしてください。

## セッション中の進め方

### 用語集と照合して指摘する

ユーザーが `CONTEXT.md` に定義された言葉と矛盾する用語を使ったら、即座に指摘してください：「用語集では『キャンセル』は X と定義されていますが、今おっしゃったのは Y の意味ではないですか？どちらが正しいですか？」

### 曖昧な言葉を精緻化する

ユーザーが曖昧な言葉や意味が重複する言葉を使ったら、正確な正規用語を提案してください。「『アカウント』とおっしゃっていますが、Customer と User のどちらを指していますか？これらは別の概念です。」

### 具体的なシナリオで検証する

ドメインの関係性について議論するときは、エッジケースを突く具体的なシナリオで検証し、概念の境界を明確にするよう促してください。

### コードと照合する

ユーザーが何かの仕組みを説明したら、コードが同じことを言っているか確認してください。矛盾があれば表面化させてください：「コードでは Order 全体がキャンセルされていますが、今おっしゃったのは部分キャンセルが可能ということですか？どちらが正しいですか？」

照合は現在のリポジトリのみを対象にしてください。

### CONTEXT.md をその場で更新する

用語が確定したら、まとめず今すぐ `CONTEXT.md` を更新してください。形式は `references/CONTEXT-FORMAT.md` に従ってください。

`CONTEXT.md` は**純粋な用語集**です。以下は記載しないでください：

- ドメインルールや不変条件
- コンテキスト間の関係図や説明
- 実装詳細・仕様・メモ
- ADR の内容

これらは別のドキュメントにまとめてください。

### 未実装のルールを DOMAIN-RULES.md に記録する

ドメインルール・不変条件・ポリシーが出てきて、**まだコードで表現されていない**場合は、`CONTEXT.md` の隣の `DOMAIN-RULES.md` に記録してください。形式は `references/DOMAIN-RULES-FORMAT.md` に従ってください。

`DOMAIN-RULES.md` は**一時的な作業成果物**です。ルールがコードに実装されたら `[ ]` を `[x]` にチェックし、実装場所を記録してください。すべての項目が `[x]` になったらファイルを削除してください——コードが正式な情報源です。

すでにコードで適切に表現されているルールは記録しないでください。

### ADR は慎重に提案する

以下の**3条件をすべて満たす**ときのみ ADR の作成を提案してください：

1. **取り消しが難しい** — 後から考えを変えるコストが相当かかる
2. **コンテキストなしでは奇妙に見える** — 将来の読者が「なぜこうしたのか？」と疑問に思う
3. **本物のトレードオフがあった** — 複数の選択肢があって特定の理由でこれを選んだ

3条件のどれか一つでも欠けていれば、ADR は不要です。コードやコードコメントで決定を明確に表現できる場合はそちらを優先し、コードだけでは判断できない場合にのみ ADR に昇格させてください。

形式は `references/ADR-FORMAT.md` に従ってください。
