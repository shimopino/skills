# Stacked PRs

## 入力

- 会話や資料に示された変更目的、期待動作、制約、検証条件。
- 関連コード、用語、設計判断（あれば）。
- 任意の出力先。ユーザー指定またはプロジェクトの慣習に従い、なければ会話内で計画を返す。

特定の仕様ファイル名、作成元、ルールやテストの ID 形式を要求しない。重要な動作や制約が不明なら、該当部分の計画前に確認する。

## 判断

各マージ時点で対象ブランチを健全に保つ。

1. ビルド、テスト、リントが通る。未参照の型の追加は許容する。
2. 利用者から見える変化がないか、その段階で完結する。機能フラグの裏の変更も含む。

宣言した先行 PR がマージ済みの状態で各段階を評価する。後続 PR がなければ正しく動かない分割はしない。

1. 各要件が関係するモジュールやパッケージを特定する。
2. コード量ではなく役割で分け、各段階の役割を1文で説明する。
3. 依存順を明示し、下の段階が後続に依存しないようにする。
4. マージごとの動作を確認する。不健全な分割は `references/layer-template.md` を参照して見直す。
5. 各段階に要件とテストを対応付ける。元資料に ID があれば使い、なければ内容で参照する。

層の順序は固定しない。型、業務ルール、永続化、API/UI は出発点の一例であり、必須の構造ではない。

## 出力

`references/layer-template.md` をプロジェクトの慣習に合わせ、実装計画を作る。要件とテストの対応は計画内に記録する。元の仕様書に特定の形式を要求せず、書き換えない。

成果物は計画と検証条件。実装と PR 作成はこのスキルの範囲外。
