# glossary

設計の会話中に、プロジェクトの言葉を能動的に鍛えて記録する。用語が固まった瞬間に書く。

## 振る舞い

1. **既存の glossary を読む**: `docs/groundwork/glossary.md` があれば最初に読む。
2. **用語を挑戦する**: ユーザーの言葉が既存定義と衝突したらその場で指摘する。「glossary では『キャンセル』を X と定義していますが、いま Y の意味で使っていませんか」。過負荷な語（「アカウント」「ユーザー」「注文」）は、どの概念を指すか確認する。
3. **コードと照合する**: ユーザーが「こう動く」と言ったら、コードが同意するか確認する。矛盾があれば口に出す。「コードは注文全体をキャンセルしていますが、部分キャンセルが可能と言われました。どちらが正しいですか」。
4. **エッジケースで定義を試す**: 新しい用語が出たら、その定義が壊れそうなシナリオを 1 つ挙げて確認する。
5. **確定した用語だけ書く**: 合意が取れた瞬間に glossary.md を更新する。暫定・議論中の語は書かない。
6. **好みとの衝突**: `preferences` の原則と衝突する命名や概念構造がプロジェクト側にあるなら、一度だけ 1 行で指摘し、プロジェクトの言葉に従う。

## glossary.md の規律

- 用語の定義だけを書く。実装詳細・仕様・作業メモ・決定事項は書かない（決定は `adr`）。
- 1 用語 = 見出し 1 つ + 1〜3 文の定義 + 必要なら「似て非なる語」への言及。
- ファイルは書くものがあるときだけ作る（空の雛形を作らない）。

## 書式

```markdown
# 用語集

## <用語>

<定義。何であり、何でないか。>
関連: [[<別の用語>]]
```
