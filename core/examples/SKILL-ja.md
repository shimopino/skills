# 実例マッピング

具体的な実例と体系的なテスト設計で業務ルールの穴を見つける。

## 入力

- 会話、仕様書、その他の資料に示された業務ルール。
- 既存用語と実例（あれば）。特定の資料や文書形式は要求しない。
- 任意の出力先または更新対象文書。指定やプロジェクトの慣習に従い、なければ会話内で返す。

## 判断

1. ルールを R1、R2 のように1文ずつ列挙し、解釈が曖昧な箇所を確認する。
2. 各ルールに最低1つ、境界があれば両側の実例を付ける。「前提 / 操作 / 期待結果」で書き、実例を作れない曖昧さは疑問として記録する。
3. 未解決の疑問を分離し、答えを捏造しない。担当者と期限は、提示されているかユーザーの進め方に必要な場合に記録する。
4. `references/techniques.md` を読み、ルールの形に該当する技法だけを適用する。
5. 実例と技法の表からテストケースを作り、由来を残す。テストレベルは判断できる情報がある場合だけ付ける。

十分に明確なルールがなければ、不足する動作や具体例を質問し、未解決事項を示す。未定義語は既存定義があれば参照して、その意味を直接確認する。

## 出力

ルール、実例、未解決の疑問、該当する技法の表、由来を追跡できるテストケースを返す。既存文書があればその形式に合わせ、それ以外は次を使う。

```markdown
# <機能名> 仕様

## 用語
<必要な定義またはリンク>

## ルール
- R1: <業務ルール>

## 実例
| ID | ルール | 前提 | 操作 | 期待結果 |
|----|--------|------|------|----------|
| E1 | R1 | | | |

## 未解決の疑問
- Q1: <疑問>

## 技法の適用
<該当する表のみ>

## テストケース
| ID | 由来（実例または表の行） | 期待動作 | テストレベル（分かる場合） |
|----|--------------------------|----------|---------------------------|
| TC1 | E1 | | |
```

ユーザーの業務の言葉で実例を書き、技術的な準備は前提欄に書く。使わない技法の見出しは省く。
