# プロジェクトの決定が勝つ

## ルール

1. プロジェクトの ADR、glossary、既存コードの一貫した慣習は、references/ のどの原則よりも優先する。
2. 衝突に気づいたら、**一度だけ、1 行で**指摘する。「好み（代数的モデリング）とは違うが、ADR-0007 の継承ベース設計に従う」。以後は繰り返さない。
3. 逸脱をプロジェクト側に持ち込みたい場合は、`adr` の 3 条件で判断し、満たすなら ADR として提案する。満たさないなら好みを引っ込める。
4. 「プロジェクトの慣習」は、複数箇所で一貫して現れるものに限る。1 箇所だけの書き方は慣習ではない。

## 効き方

- Java 17 以前のプロジェクトでは references/algebraic-modeling.md の sealed/record 前提を緩める根拠になる。
- チームが例外ベースで統一している場合、結果型を持ち込まない根拠になる。

## 参考

pstack には直接の対応原則はない。ADR を掘り起こす `/why` が、決定が記録されていない場合の代替手段。
