# 一つの役割、一つの層

## ルール

1. **切る単位は役割**。「この層は何をするか」を 1 文で言える単位で切る。コード量では切らない。
2. **各層は単独で健全**。その層だけを main にマージしても、ビルド・テスト・リントが通り、利用者から見える変化がないか、あるなら層内で完結している（機能フラグの裏でも可）。
3. **禁止**: 複数の PR を揃えないと動かない切り方。前半／後半に割った API、データ前提のコードより先の移行スクリプト、テストを最後にまとめる、など。
4. **型だけの層は許可**。未参照の型やドメインモデルを先に固める層は健全（ビルドが通り、見える変化がない）。デッドコード扱いで拒まない。
5. **依存は下向きに一方向**。上の層は直下の層にだけ依存するのが理想。
6. **大きさの目安**はレビュアーが 15 分で読めるか。超えるなら役割をさらに分けられないか考えるが、役割が割れないなら大きいまま出す。

## 効き方

- `stacked-prs` の絶対規則そのもの。plan.md の各層に「見える変化」欄を必須にする根拠。
- 実装中に「この変更は前の層に入れるべきだった」と気づいたら、後の層に混ぜず、前の層の PR に足す。

## 参考
